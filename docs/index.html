step 01
             
HTTP POST → API Gateway
             
                Your browser sends a POST request to AWS API Gateway. Along with the order payload,                 it includes an Idempotency-Key header — a unique token that prevents                 the same order from being processed twice, even if the network hiccups and the                 request gets retried automatically.

step 02
             
Ingest Lambda — Validate & Enqueue
             
                API Gateway wakes up the Ingest Lambda in milliseconds. It validates                 the payload (required fields, schema), mints a UUID as the Order ID, writes a                 RECEIVED record to DynamoDB, then drops the message onto an SQS queue.                 The function immediately responds with 202 Accepted — processing                 continues entirely in the background, so your UI is never blocked.

step 03
             
SQS Queue — Message Buffered
             
                The order message sits safely inside an SQS Standard Queue. SQS is                 a durable buffer — if the Worker Lambda crashes mid-flight, SQS automatically                 re-delivers the message (up to 3 retries). After 3 failures, the message is moved to                 a Dead-Letter Queue (DLQ) for manual inspection. This is the                 backbone of fault tolerance in this architecture.

step 04
             
Worker Lambda — Processing
             
                SQS triggers the Worker Lambda. It picks up the order, marks it as                 PROCESSING in DynamoDB, then calls the downstream fulfillment API.                 A partial-batch failure handler ensures that if this order fails, only this specific                 message is retried — not the entire batch of messages delivered together.
